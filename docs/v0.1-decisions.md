# Decisions for v0.1

The design notes left a few questions open. These are the answers the compiler ships with.

## Seal keys are seeds

`mohar keygen` writes a 32-byte ML-DSA-65 seed (`MOHAR KEY v1`) and a sibling `.pub` file with the encoded verifying key. RustCrypto's preferred private-key form for ML-DSA is that seed (`ML-DSA.KeyGen_internal`). A PKCS#8 wrapper can wait until the crate's PKCS#8 support is the path we want to support in documentation. The public key id is SHA3-256 of the encoded verifying key.

## Secret text is not indexed

Indexing a `secret Text` is `E102`. v0.1 does not choose between byte offsets and scalar offsets, because either one is a leaky encoding question and neither is needed for the examples. Byte arrays are the type for secret material.

## Plan allows non-recursive functions

A `plan` program may define functions. The call graph from `main` must be acyclic (`E210`), and `while` is rejected (`E211`). Forbidding every helper would have made `count_words` illegal in a plan for no gain. The totality argument is "the call graph is a DAG and every loop is a `for` over a value whose bounds are not secret."

## Directory entries are trusted metadata

`FsRead::list` returns `List<Text>` with a public trusted element type. File *contents* from `read` and `read_text` are untrusted. This is a choice: a hostile name inside a granted directory cannot, by itself, taint the program counter of the loop that lists it. The bytes of the file still can. It is recorded here because a reviewer will ask.

## Lengths are a size channel

`.len()` preserves confidentiality (a secret collection has a secret length) and does not preserve integrity (the length of untrusted text is a public `u64`). The README lists this under the limits. It is why `count_words` can return `u64` as written in the design.

## The hybrid is not X-Wing

`Kem::default` under `pq-hybrid` is X25519 plus ML-KEM-768, concatenated and passed through HKDF-SHA3-256 with info `mohar-hybrid-v1`. The `x-wing` crate tracked an older draft at the time of the design, so v0.1 does not claim that name. The seal says `X25519-MLKEM768`.

## ECDSA and the signature crate

`slh-dsa` 0.1.0 depends on a pre-release of the `signature` crate (`2.3.0-pre.4`, pinned). Current `p256` 0.13 cannot sit in the same dependency graph. v0.1 links `p256` 0.11 so ECDSA P-256 actually runs, for the `Q101` lint and for tests. RSA-PSS is named for the policy and the CBOM and returns an error if called: a second multiprecision stack was not worth linking. That is a gap, not a permanent answer.

## `aws-lc-rs` is not linked

The design allows it as a second backend behind the same trait. v0.1 has the RustCrypto backend only. The trait-shaped modules in `mohar-std` are where a second backend would go. The docs tell you to use an audited library if you need one; they do not pretend this tree contains one.
